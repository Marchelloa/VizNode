# Правила работы Codex

## Изменения только после подтверждения

Codex не должен самостоятельно изменять файлы проекта.

Перед любым изменением Codex обязан:

1. Описать обнаруженную проблему или задачу.
2. Предложить один или несколько вариантов решения.
3. При необходимости показать небольшой прототип или пример предполагаемых изменений.
4. Кратко объяснить логику, последствия и компромиссы каждого варианта.
5. Получить явное подтверждение пользователя.

Только после явного подтверждения разрешается изменять файлы.

Без дополнительного подтверждения разрешены только действия чтения и анализа:

- просмотр файлов;
- поиск по проекту;
- проверка состояния Git;
- запуск безопасных диагностических команд;
- изучение логов и результатов тестов.

Разрешение на одно изменение не распространяется автоматически на последующие изменения.
Если в ходе работы возникает необходимость изменить дополнительные файлы или расширить согласованный объём, Codex должен снова запросить подтверждение.

## Работа с Git

Команды Git, изменяющие состояние репозитория или удалённых веток, пользователь вводит самостоятельно. Codex не выполняет их, а показывает точные команды в порядке выполнения и кратко объясняет, что каждая команда изменяет и зачем нужна.

Это относится к staging, коммитам, созданию и переключению веток, merge, rebase, stash, reset, restore, clean, fetch, pull, push, тегам и worktree. Просьбы «коммитим», «отправляем» и подобные означают подготовку команд для пользователя, а не их выполнение Codex.

Перед подготовкой команд Codex проверяет состав изменений и явно указывает, какие файлы и ветки затрагиваются. После выполнения пользователь сообщает результат; дальнейшие команды подбираются с учётом этого результата.

Чтение состояния и истории Git (`status`, `diff`, `log`, `show`, просмотр веток) Codex может выполнять для анализа.

## Исключение для команд демо

Если сообщение начинается с `демо:` или `demo:`, текст после префикса считается явным разрешением на изменения фронтенда работающего демо без дополнительного подтверждения. Это исключение имеет приоритет над общим правилом подтверждения в пределах указанного запроса.

Разрешены изменения оформления, разметки и клиентского представления во время работы приложения. Изменения бизнес-логики, серверной части, данных, зависимостей и настроек проекта требуют отдельного согласования. Если запрос выходит за эти границы, необходимо запросить подтверждение.

## Разделение структурных изменений и изменений поведения

При архитектурном рефакторинге, особенно при переносе существующей логики между модулями и выделении новых абстракций, Codex обязан:

- на первом этапе изменять только организацию кода, зависимости и границы ответственности компонентов;
- сохранять существующие алгоритмы, контракты, последовательность операций и наблюдаемое поведение приложения;
- не совмещать перенос логики с её оптимизацией, упрощением, переосмыслением или добавлением функциональности;
- обнаруженные архитектурные недостатки, потенциальные ошибки и возможности улучшения фиксировать отдельно, не исправляя их в рамках текущего переноса без согласования;
- после переноса проверять функциональную эквивалентность исходной и новой реализации;
- только после успешного завершения структурного этапа предлагать дальнейшие архитектурные улучшения отдельными шагами.

Цель — обеспечить контролируемую эволюцию архитектуры, при которой возможные регрессии можно однозначно связать с конкретным изменением.

## Комментарии и JSDoc

Комментарии должны помогать понять код, а не усложнять его чтение.

- писать кратко и понятно, на русском языке, сохраняя имена API и терминов кода;
- объяснять архитектурные границы, причины неочевидных решений, инварианты и важные побочные эффекты;
- не пересказывать соседние строки кода и не документировать очевидные функции только ради наличия комментария;
- использовать обычные комментарии для локальных пояснений, JSDoc — для полезного описания контракта функции;
- добавлять `@param` и `@returns` там, где они уточняют неочевидную структуру данных, результат или помогают редактору; не добавлять `@returns {void}` и `@returns {Promise<void>}` без необходимости;
- не вводить сложные типовые конструкции и длинные `@typedef`, если краткого пояснения достаточно; повторяющиеся структурные типы описывать отдельно только при реальной пользе для чтения и подсказок редактора;
- явно различать описание типа, объекта и функции; размещать комментарий рядом с тем, что он описывает;
- сохранять пояснения о порядке операций, ожидании Promise, фоновых действиях, очередях и сохранении локального ввода, если эти гарантии неочевидны из кода;
- не использовать декоративные разделители и заголовки, дублирующие понятную структуру файла;
- поддерживать комментарии в соответствии с фактической реализацией; при изменении только документации не менять исполняемый код.
