## Коротко О Проекте

VizNode — это `console-first` прототип.

Основная идея:

- пользователь решает задачу через чистый консольный интерфейс
- интерфейс показывает только то, что нужно для текущего действия
- HTML нужен не как второй живой UI, а как snapshot текущей ноды или экрана по запросу

## Главная Ментальная Модель

Проект сейчас лучше всего держать в голове так:

`state -> tree -> renderer -> console interaction`

Дополнительно:

- `server.js` эмулирует backend-поведение
- `observer.js` дает каналы событий
- `effects.js` логирует side effects и notices

## Кто За Что Отвечает

### `src/app.js`

Главный orchestration-layer.

Здесь живут:

- запуск приложения
- `readline` loop
- обработка действий
- обработка ввода в поля
- `submitTransferFlow()`
- локальная валидация формы перевода

### `src/state.js`

Хранит клиентское состояние:

- `screen`
- `balance`
- `transferForm`

И дает:

- `setByPath(...)`

### `src/tree.js`

Собирает дерево интерфейса на основе текущего `state`.

Не рендерит.
Только описывает структуру экрана.

### `src/nodes.js`

Фабрики нод:

- `textNode`
- `actionNode`
- `inputNode`
- `menuNode`
- `containerNode`

### `src/renderer.js`

Рендерит дерево в консоль.

Отвечает за:

- вывод текста
- вывод action/input-пунктов
- нумерацию
- `actionMap`

### `src/server.js`

Эмуляция серверной логики.

Сейчас отвечает за:

- `executeTransfer(...)`
- проверку перевода
- изменение серверного баланса
- возврат `ok/error`

### `src/observer.js`

Разделяет два типа событий:

- `state` changes
- `app` events

Главные функции:

- `notifyStateChanged(...)`
- `notifyAppEvent(...)`

### `src/effects.js`

Логирует побочные эффекты и сообщения.

Сейчас там:

- `[STATE] ...`
- `[EVENT] ...`
- `[NOTICE] ...`
- demo server logs

### `.vscode/launch.json`

Хранит быстрый запуск проекта из VS Code.

Сейчас настроено:

- конфигурация `Run VizNode CLI`
- запуск `src/app.js`
- работа через `integratedTerminal`

Если нужно быстро запустить прототип в VS Code:

1. Нажать `F5`
2. Выбрать `Run VizNode CLI`

## Основной Flow Перевода

Текущий сценарий перевода выглядит так:

1. Пользователь открывает экран перевода.
2. Пользователь выбирает поля и вводит значения.
3. `handleInputEdit(...)` обновляет `state.transferForm`.
4. Пользователь нажимает `Submit`.
5. `submit_transfer` запускает `submitTransferFlow()`.
6. Локальная валидация проверяет форму.
7. Клиент вызывает `server.executeTransfer(...)`.
8. Если ответ успешный:
   - обновляется `state.balance`
   - очищается `transferForm`
   - меняется `screen`
   - отправляется `transfer_applied`
   - отправляется notice `Transfer completed`

## Важный Нюанс Про `loop()`

Самая частая ловушка сейчас — это повторный вызов `loop()` не в том месте.

Правильная модель:

- `loop()` рендерит экран
- ждет пользовательский ввод
- после обработки снова запускается

Но для input-поля есть отдельный подшаг:

1. Пользователь выбирает input.
2. `handleInputEdit(...)` вызывает `rl.question(...)`.
3. Пользователь вводит значение.
4. Только после callback нужно снова вызывать `loop()`.

Важно:

- нельзя вызывать `loop()` сразу после `handleInputEdit(...)` снаружи
- иначе появятся два конкурирующих `rl.question(...)`
- визуально это выглядит как "консоль зависла"

Канал уже выделен правильно, но еще стоит осмыслить:

### 4. `package.json`

Нужно привести в соответствие текущему проекту:

- проверить `main`
- добавить нормальный `start`-script
- сверить запуск через `npm start` с VS Code launch flow

## Что Пока Не Нужно Делать

- не нужно срочно дробить `app.js`
- не нужно выносить `submitTransferFlow()` раньше времени
- не нужно строить полноценный HTML UI
- не нужно усложнять event-system без реальной необходимости

## Ближайший Практичный План

1. Починить кодировку в проекте.
2. Упростить и стабилизировать UX после `submit`.
3. Привести `package.json` к рабочему виду.
4. Сверить, что VS Code запуск и `npm start` ведут в одну точку входа.
5. Решить, какие `app events` остаются как постоянная модель.
6. Только потом двигаться к HTML snapshot renderer.
