# Срез Архитектуры VizNode

## Текущее Состояние

Прототип уже перестал быть одиночным demo-скриптом. Сейчас он больше похож на маленькое приложение с разделением на несколько слоёв:

- `src/app.js`
  - точка входа приложения
  - цикл `readline`
  - маршрутизация действий
  - обработка ввода
  - сценарий отправки перевода
- `src/tree.js`
  - собирает дерево интерфейса из текущего состояния
- `src/nodes.js`
  - фабрики UI-нод
- `src/renderer.js`
  - рендерит дерево в консоль
  - возвращает `actionMap` для взаимодействия с пользователем
- `src/state.js`
  - состояние приложения
  - обновление состояния по пути
- `src/observer.js`
  - механизм подписки на изменения состояния
- `src/effects.js`
  - логирование side effects
  - demo-сообщения, связанные с серверной обработкой
- `src/server.js`
  - фейковый backend
  - правила выполнения перевода

## Что Уже Выглядит Хорошо

- Построение UI-дерева отделено от консольного рендера.
- Клиентский сценарий перевода отделён от серверного выполнения перевода.
- Редактирование инпутов сделано обобщённо через `bind` и `setByPath(...)`.
- Observer и effects вынесены из основного потока приложения.
- `submitTransferFlow()` остаётся на клиентской стороне, и это правильная граница ответственности.

## Текущая Карта Ответственности

### Клиентская Сторона

- читать пользовательский ввод
- локально валидировать форму перевода
- вызывать сервер
- обновлять клиентский `state` по ответу сервера
- переключать экраны

### Серверная Сторона

- принимать запрос на перевод
- валидировать бизнес-правила
- изменять серверный баланс
- возвращать ответ `ok/error`

### Слой Представления

- описывать экран в виде дерева нод
- рендерить дерево в консоль
- связывать номер действия с конкретной нодой

## Важные Нюансы

### 1. Сейчас Есть Два Баланса, И Это Осознанно

Баланс сейчас существует в двух местах:

- `src/state.js` как баланс, который видит клиент
- `src/server.js` как баланс, принадлежащий серверу

Для прототипа это допустимо, но важно держать такую ментальную модель:

- серверный баланс является источником истины
- клиентский баланс является копией, которая обновляется из ответа сервера

### 2. Уведомления И Изменения Состояния Пока Немного Смешаны

Сейчас сообщения вроде `Transfer completed` проходят через `notifyStateChanged(...)`.

Технически это работает, но по смыслу это не совсем изменение состояния. Это скорее:

- уведомление
- effect event
- обратная связь для пользователя

Срочного рефакторинга здесь не требуется, но именно в этом месте сейчас находится основная размытость архитектуры.

### 3. `app.js` Пока Нормален, Но Уже Становится Координационным Центром

Это нормально. Сейчас `app.js` отвечает за оркестрацию, и это валидная роль.

Он должен оставаться местом для:

- bootstrap-логики
- управления циклом
- маршрутизации действий
- координации отправки перевода

И постепенно не должен превращаться в место для:

- низкоуровневых серверных правил
- деталей рендера
- деталей реализации effects

## Что Пока Не Нужно Выносить

Срочного выноса не требуется для следующих частей:

- `submitTransferFlow()`
- `validateTransferForm()`
- `handleAction()`
- `handleInputEdit()`

Сейчас их по-прежнему разумно держать в `src/app.js`, потому что они относятся к оркестрации пользовательского сценария.

## Где Скорее Всего Появится Следующее Давление

Если сложность продолжит расти, следующими кандидатами на вынос могут стать:

### Вариант A: Клиентский Flow Перевода

Возможный файл:

- `src/transferFlow.js`

Возможное содержимое:

- `submitTransferFlow()`
- локальная валидация, связанная с переводом

### Вариант B: Пользовательские Уведомления

Возможный файл:

- `src/notifications.js`

Возможное содержимое:

- диспетчеризация уведомлений
- временные сообщения
- разделение между state events и user-facing messages

### Вариант C: Обработчики Действий Приложения

Возможный файл:

- `src/actions.js`

Возможное содержимое:

- `actionHandlers`
- обработчики переходов между экранами

Это станет полезно только если количество действий заметно вырастет.

## Предлагаемый План

### Этап 1: Стабилизировать Текущую Структуру

- сохранить текущее разбиение по файлам
- не переносить код только ради внешней аккуратности
- продолжать добавлять фичи внутри текущих границ ответственности

### Этап 2: Уточнить Семантику Событий

- отделить изменения состояния от уведомлений
- решить, как именно логировать сообщения об успехе и ошибках:
  - как state events
  - как effect events
  - как UI messages

### Этап 3: Улучшить UX Во Время Submit

- определить, что пользователь должен видеть во время `submit`
- выбрать один из вариантов:
  - возврат на `main`
  - переход на `balance`
  - показ временного статусного сообщения

### Этап 4: Выносить Только При Реальном Давлении

Создавать новый файл только если выполняется одно из условий:

- `app.js` становится трудно быстро просканировать глазами
- flow перевода вырастает больше одного сфокусированного блока
- логика уведомлений начинает расползаться по модулям
- действия становятся многочисленными и однотипными

## Рабочее Правило Для Будущих Рефакторингов

Перед тем как выносить код, стоит спросить себя:

1. Это новая ответственность или просто стало больше строк?
2. Новый файл уменьшит связанность или только переставит код местами?
3. После переноса проект станет понятнее?

Если ответ не выглядит уверенным "да", лучше пока оставить код на месте.
