# VizNode — контекст для продолжения разработки

Актуализировано: 15 сентября 2026 года.

## Идея и архитектура

VizNode исследует заменяемый интерфейс, построенный из доверенного состояния и разрешённых действий пользователя. Представление отделено от прикладной логики. Общий замысел описан в README.md и docs/ideas/ai-driven-dom-interface.md.

Node runtime — единственный владелец state, application.dispatch(event), доверенных handlers и построения декларативного дерева интерфейса. Console и DOM одновременно отображают одно работающее приложение. Браузер не импортирует state, не создаёт application и не строит дерево самостоятельно.

Текущий цикл:

```text
Console event ─┐
               ├→ application.dispatch(event) → state → buildTree(state)
DOM event ─────┘                                         ├→ Console render
                                                        └→ SSE → DOM render
```

Console и DOM должны оставаться взаимозаменяемыми представлениями. В дальнейшем любой renderer можно будет подключать и отключать по запросу, не создавая отдельного состояния.

## Контракт представления

state хранит экран, баланс, форму перевода и статус. buildTree(state) возвращает декларативное дерево интерфейса: это не дерево состояния и не DOM-дерево. Оно независимо от renderer описывает содержимое, структуру и разрешённые взаимодействия.

Корень дерева — массив нод. Текущие типы: text, action, input, menu (props.items), container (props.children).

Renderer преобразует пользовательские действия в нормализованные события:

```js
{ type: "action", intent: "show_balance" }
{ type: "input", bind: "transferForm.amount", value: "500" }
```

Обработчики и изменение состояния остаются в application.dispatch(event). Строгая схема дерева, рекурсивная валидация и allowlist внешних intent/bind пока не реализованы.

## Реализованный общий цикл

### Node → DOM

1. Браузер открывает EventSource на http://127.0.0.1:3000/api/events.
2. GET /api/events создаёт SSE-ответ; мост сохраняет response в Set клиентов.
3. Новый клиент сразу получает getCurrentTree(), поэтому открывается на текущем экране приложения, а не на стартовом.
4. loop() строит дерево один раз, передаёт его в Console renderer и publishTree(tree).
5. Браузер получает JSON через SSE и вызывает renderDOM(tree, root).
6. После разрыва соединения response удаляется из Set; EventSource автоматически переподключается.

### DOM → Node

1. browser-demo.js делегирует click от #app к ближайшему элементу с data-intent.
2. Нормализованное action-событие отправляется POST-запросом на /api/dispatch.
3. browser bridge вызывает переданный application.dispatch(event).
4. Изменение state вызывает общий requestRender/loop.
5. Одно новое дерево одновременно отображается в Console и отправляется в DOM через SSE.

OPTIONS /api/dispatch обслуживает CORS preflight для страницы, открытой через Live Server. Неверный JSON получает 400, отклонённое приложением событие — 400, внутренняя ошибка dispatch — 500, неизвестный маршрут — 404.

## DOM-ввод: очередь и локальный черновик

input-слушатель читает data-bind и value, сохраняет новый объект `{ value, accepted: false }` в pendingInputs и отправляет input-событие. dispatchEvent использует lastDispatchPromise: каждый HTTP-запрос ждёт завершения предыдущего, включая действия после ввода. Ошибка передаётся вызывающему коду, но цепочка продолжает работать.

HTTP-ответ отмечает только объект своего ввода как accepted, не более новый объект того же bind. collectInputValues рекурсивно собирает значения последнего SSE-дерева в confirmedInputs. removeConfirmedPendingInputs удаляет последнюю pending-запись, когда accepted=true и значение совпало с SSE. Проверка вызывается после обоих сигналов, поскольку HTTP и SSE могут прийти в любом порядке.

renderDOM(tree, root, pendingInputs) заменяет DOM, восстанавливает неподтверждённые значения, затем фокус и выделение по data-bind. Node остаётся владельцем общего состояния; pendingInputs — временный локальный ввод, не второе application state. Console показывает обработанные значения Node, DOM может кратковременно показывать более свежий текст.

Выбран режим отдельного input-события на каждую правку поля; action запускает операцию над общим state, а не передаёт форму в payload. Подтверждение по значению временное: повторяющиеся значения и конкурентное редактирование требуют идентификаторов событий или ревизий.

## Console lifecycle

Console использует один постоянный rl.on("line", handleConsoleLine), актуальные currentActionMap и pendingInputNode. loop() больше не создаёт вложенные readline.question при каждом рендере. Это важно, потому что requestRender теперь может быть вызван действием как из Console, так и из DOM.

Во время асинхронной фазы sending новый prompt не выводится. После завершения операции следующий requestRender обновляет оба renderer и возвращает приглашение Console.

## Переключаемое оформление

styles.css содержит только выбор активного пресета через @import. Сейчас активна ретро-консольная тема:

```css
/* @import "./styles.base.css"; */
/* @import "./styles.bank.css"; */
/* @import "./styles.lab.css"; */
@import "./styles.terminal.css";
```

Для демонстрации достаточно поменять активную строку импорта. Это изменяет уже отображённую страницу, не перестраивает state и не заменяет #app.

Основной index.html содержит постоянную декоративную оболочку. Банковская тема показывает эмблему, статус сессии и подвал. Базовая тема скрывает их через display: none и использует display: contents для оболочки. Так тема может менять не только цвета, но и окружающее оформление, не вмешиваясь в декларативное дерево приложения.

Лабораторная тема создана на ходу как новый CSS-пресет: светлые карточки, бирюзовые акценты и медицинская эмблема. HTML и банковские подписи не менялись. Terminal-пресет первоначально создавался для index.terminal.html; его собственная оболочка отсутствует в основном index.html, поэтому переключение CSS не воспроизводит всю отдельную terminal-страницу.

Попытка генерации медицинского фонового изображения дважды завершилась ошибкой соединения. Изображение не создано, CSS на него не ссылается.

## Что проверено

- Доставка начального дерева и последующих обновлений по одному SSE-соединению.
- Подключение DOM на текущем экране Console.
- OPTIONS /api/dispatch: статус 204 и нужные CORS-заголовки.
- Некорректный JSON: 400.
- Неизвестное action-событие: handled false и 400.
- Реальное действие open_transfer: handled true и 200.
- Сквозные DOM-переходы Transfer и Back: одновременно обновлялись Console и DOM.
- Полный Console-сценарий перевода: форма, ввод получателя и суммы, отправка, успешный статус и новый баланс.
- Банковская и terminal-темы визуально проверялись на главном экране и Transfer Form.

npm test пока является заглушкой; постоянного набора автоматических тестов нет.

Пользователь подтвердил пригодность текущего прототипа для демонстрации. Новые механизмы DOM-input, очереди и подтверждений пока не имеют зафиксированной сквозной проверки под задержками; не считать её выполненной по одному факту наличия кода.

## Текущие ограничения

- DOM-input подключён, но быстрый ввод, отправка формы и переключение между renderer требуют сквозных проверок.
- Подтверждение ввода основано на совпадении значений, а не идентификаторе события или ревизии.
- При отклонении или ошибке input запись pending остаётся; нужно определить повтор, откат и уведомление пользователя.
- При исчезновении поля pending-запись может остаться и позднее перекрыть данные вновь открытой формы.
- Ошибка input не блокирует следующий action, поэтому перевод может использовать старые данные после неудачной отправки поля.
- replaceChildren создаёт поля заново; IME/composition, undo и несколько вкладок пока не проверены.
- Внешние события пока не проходят строгую проверку структуры и allowlist.
- HTTP body не имеет ограничения размера.
- CSS-пресеты переключаются вручную изменением styles.css; runtime API для тем пока не нужен.

## Ближайшие шаги

Работать небольшими согласованными шагами, не добавляя новые архитектурные слои до закрепления текущего потока.

1. Проверить полный Transfer Form из DOM: получатель, сумма, быстрый набор и немедленный Submit, sending, success/error и баланс.
2. Проверить сохранение текста, фокуса и курсора при задержанных SSE-обновлениях.
3. Проверить продолжение сценария Console → DOM и обратно, смену экрана и повторное открытие формы.
4. Определить обработку rejected/error input и запрет зависимого action при неподтверждённых данных.
5. Заменить неоднозначное подтверждение по значению явными идентификаторами/ревизиями перед расширением на конкурентных клиентов.
6. Стабилизировать lifecycle и добавить автоматические тесты dispatch, bridge и DOM-ввода.

После этого: строгая схема и рекурсивная валидация дерева, allowlist intent/bind, контракт InterfaceBuilder и deterministic provider, затем необязательный AI provider с безопасным fallback.

AI может выбирать оформление и компоновать разрешённые ноды. Он не должен генерировать исполняемый JavaScript, создавать handlers, напрямую менять state или обходить dispatch. Полученное дерево должно проходить валидацию до renderer.

## Запуск

1. npm start — запускает Console и HTTP/SSE-мост.
2. Открыть index.html через Live Server, обычно http://127.0.0.1:5500/index.html.
3. Действия и редактирование полей доступны как в Console, так и в DOM.

Закрытие вкладки не останавливает Node. Завершение Console останавливает весь runtime.

## Порядок работы

Пользователь проектирует и создаёт технологию, предпочитает вводить код самостоятельно и сохранять контроль над потоком и архитектурными решениями. Codex объясняет поток и проверяет результат. Codex редактирует файлы только после отдельного явного согласования согласно корневому AGENTS.md. Для быстрых демонстраций оформления пользователь разрешает переключать заранее подготовленные CSS-пресеты по прямому запросу.

При продолжении прочитать этот документ, AGENTS.md, проверить git status и актуальный код. Не создавать отдельное состояние браузера и не возвращать удалённый /api/tree. DOM-ввод реализован на базовом уровне, но его ограничения и незавершённые проверки описаны выше. Согласовано фиксировать этот этап на локальной main и fast-forward синхронизировать prototype; push требует отдельного запроса.
