# VizNode — контекст для продолжения разработки

## Назначение документа

Этот файл фиксирует архитектурный замысел, фактическое состояние прототипа и ближайший порядок работы. Он предназначен для быстрого продолжения проекта на другом компьютере или в новой сессии без восстановления контекста из истории обсуждений.

## Актуализация плана: общее состояние Console и DOM

Эта секция фиксирует уточнение от 3 сентября 2026 года и имеет приоритет над прежними формулировками ниже, где Console и DOM описаны как независимые среды исполнения без синхронизации.

Целевая модель теперь следующая: Node runtime является единственным владельцем `state`, `application.dispatch(...)`, доверенных handlers и построения UI-дерева. Console и DOM являются подключёнными renderer одного приложения и не создают собственные экземпляры состояния.

```text
Console event ─┐
               ├→ application.dispatch(event)
DOM event ─────┘             ↓
                         единый state
                              ↓
                       buildTree(state)
                         ↙          ↘
                  Console render   DOM render
```

Основные инварианты:

- `state` является единственным источником истины;
- все подтверждённые изменения проходят через `application.dispatch(event)`;
- `buildTree(state)` является общей точкой построения декларативного представления;
- renderer только отображает полученное дерево и преобразует пользовательский ввод в нормализованные события;
- DOM не импортирует `state.js` и не создаёт собственный `application`;
- browser renderer получает готовое дерево, а не сырой `state`;
- после изменения общего состояния новый экран должен быть согласован в Console и DOM;
- незавершённый ввод в активном поле DOM может временно оставаться локальным черновиком и не синхронизироваться на каждый символ;
- перед DOM action, зависящим от формы, актуальные значения полей должны быть зафиксированы input-событиями до отправки action-события;
- закрытие DOM отключает только browser renderer: Console и Node runtime продолжают работать с тем же состоянием;
- при повторном подключении DOM сразу получает дерево актуального состояния.

Предполагаемый пользовательский сценарий:

1. Приложение запускается в Console.
2. Пользователь переходит, например, на экран `Transfer Form`.
3. Подключается DOM и сразу отображает тот же экран, а не начальный `main`.
4. После подключения действия из Console или DOM изменяют один общий `state`.
5. Подтверждённые изменения экрана, формы, статуса и баланса отображаются обоими renderer.
6. После закрытия DOM работа продолжается в Console без сброса состояния.

### Текущий пошаговый план

Работа ведётся небольшими проверяемыми изменениями. Пользователь самостоятельно вводит код, пока явно не попросит Codex внести конкретное изменение. Перед каждой правкой сохраняется правило обязательного согласования из `AGENTS.md`.

Текущее состояние шагов:

1. В `src/app.js` уже добавлена функция `getCurrentTree()`, возвращающая `buildTree(application.state)`. Console loop использует эту функцию. Добавлены JSDoc и секция `SHARED TREE`.
2. Пользователь создал `src/browser-bridge.js`. Модуль использует встроенный `node:http`, принимает callback `getCurrentTree` и обрабатывает только `GET /api/tree`. Он ещё не подключён к `src/app.js` и не проверен запуском.
3. Текущий `src/browser-demo.js` всё ещё создаёт собственный `application`, поэтому browser пока имеет отдельный экземпляр состояния. Этот код предстоит заменить после проверки HTTP-моста.

Ближайшие действия в строгом порядке:

1. Проверить синтаксис и реализацию `src/browser-bridge.js`, не подключая его автоматически.
2. Импортировать `startBrowserBridge` в `src/app.js` и запустить его с callback `getCurrentTree`.
3. Запустить Console и проверить `GET /api/tree` сначала на экране `main`, затем после перехода Console на `transfer`.
4. Переделать `src/browser-demo.js` в тонкий browser adapter: убрать локальные `createApplication` и `state`, запросить `GET /api/tree` и передать ответ в `renderDOM(tree, root)`.
5. Проверить, что при открытии или обновлении страницы DOM показывает текущий экран Console.
6. После подтверждения начального общего дерева добавить передачу нормализованных DOM-событий в Node runtime отдельным endpoint.
7. Добавить доставку нового дерева из Node в уже открытый DOM. Предпочтительный минимальный вариант без внешней зависимости: Server-Sent Events для обновлений Node → DOM и обычный `POST` для событий DOM → Node. WebSocket остаётся альтернативой, если потребуется единый двусторонний канал.
8. Ввести общий render coordinator: после принятого события он строит дерево один раз и доставляет его Console и всем подключённым browser renderer.
9. Стабилизировать перерисовку Console во время активного `readline` prompt, чтобы внешнее DOM-событие не повреждало ввод пользователя.
10. Реализовать локальные DOM-черновики полей: не синхронизировать каждый символ, фиксировать значения при завершении редактирования и обязательно перед зависимым action.
11. Проверить полный сценарий `Console → DOM → Console`, включая переходы экранов, заполнение формы, статусы асинхронного перевода, новый баланс, закрытие и повторное открытие DOM.

На текущем шаге не следует добавлять AI provider, валидатор дерева, большой UI-фреймворк или стороннюю сетевую библиотеку. Сначала должен быть доказан общий цикл одного состояния и двух renderer.

## Идея проекта

VizNode исследует пользовательский интерфейс, отделённый от представления, навязанного сервисом. Сервис и доверенный код приложения определяют факты, состояние и разрешённые операции. Способ представления выбирается отдельно.

Проект разделяет четыре ответственности:

```text
state     — что действительно происходит сейчас
intent    — что пользователю разрешено сделать
tree      — что требуется представить для текущей задачи
renderer  — как пользователь воспринимает интерфейс и управляет им
```

Основной цикл:

```text
state
  → InterfaceBuilder.buildTree(state)
  → декларативное UI-дерево
  → выбранный renderer
  → нормализованное пользовательское событие
  → application.dispatch(event)
  → доверенный handler или обновление input
  → новый state
  → повторное построение дерева
```

Console и DOM — заменяемые представления одного формата дерева. Они не должны содержать разные варианты прикладного поведения.

## State и UI-дерево — разные сущности

`state` является источником фактов приложения. Сейчас он содержит:

- активный экран;
- баланс;
- данные формы перевода;
- фазу и сообщение статуса.

UI-дерево является декларативным представлением текущего `state`. Оно не хранит бизнес-логику и не является самим состоянием.

Текущий детерминированный путь:

```js
const tree = buildTree(state);
```

Полученное дерево можно передать любому совместимому renderer:

```js
renderConsole(tree);
renderDOM(tree, root);
```

Например, когда `state.screen === "balance"`, `buildTree(state)` создаёт дерево с текстом текущего баланса и действием `back`. Console renderer показывает его строками и нумерованными пунктами, а DOM renderer — HTML-элементами. Содержание и доступные действия задаёт одно дерево, хотя визуальная форма отличается.

## Строгий контракт UI-дерева

Корень дерева сейчас является массивом нод. Разрешены пять типов:

- `text` — безопасный текст;
- `action` — действие с известным `intent`;
- `input` — поле с разрешённым путём `bind`;
- `menu` — коллекция `props.items`;
- `container` — смысловая группа `props.children`.

Пример:

```js
[
  {
    type: "text",
    props: {
      text: "VizNode Bank",
    },
  },
  {
    type: "menu",
    props: {
      title: "Main Menu",
      items: [
        {
          type: "action",
          props: {
            id: "show_balance",
            label: "Check Balance",
            intent: "show_balance",
          },
        },
      ],
    },
  },
]
```

Интерактивные renderer должны создавать нормализованные события только двух форм:

```js
{
  type: "action",
  intent: "show_balance",
}
```

```js
{
  type: "input",
  bind: "transferForm.amount",
  value: "500",
}
```

Renderer не выбирает handler самостоятельно и не изменяет `state`. Все события передаются в единый `application.dispatch(event)`.

## Роль AI

AI задуман как необязательный и заменяемый provider для `InterfaceBuilder`. Он заменяет только способ построения декларативного дерева.

```text
                 ┌→ deterministic provider
state → builder ─┤
                 └→ AI provider
                       ↓
              валидированное UI-дерево
```

AI сможет получать:

- безопасный snapshot текущего состояния;
- список разрешённых типов нод;
- allowlist разрешённых `intent`;
- allowlist разрешённых `bind`;
- правила композиции интерфейса;
- схему ожидаемого результата.

AI сможет выбирать разрешённые ноды, компоновать их и ссылаться на известные `intent` и `bind`. Он не должен:

- генерировать или исполнять JavaScript;
- возвращать произвольный HTML;
- создавать новые бизнес-операции;
- регистрировать handlers;
- менять `state` напрямую;
- обходить `application.dispatch()`;
- передавать результат renderer до успешной валидации.

Приложение остаётся владельцем настоящего `state`, разрешённых операций, проверки дерева, создания DOM и выполнения handlers.

Основная проверяемая гипотеза проекта:

```text
state → AI-интерфейс → DOM → intent → handler → новый state
```

Идея остаётся работоспособной без AI: текущий детерминированный `buildTree` должен работать за тем же контрактом.

## Текущие модули

### `src/state.js`

Хранит текущий `state` и предоставляет `setByPath(...)` для записи связанного input по точечному пути.

### `src/nodes.js`

Содержит фабрики `textNode`, `actionNode`, `inputNode`, `menuNode` и `containerNode`.

### `src/tree.js`

Содержит текущий детерминированный `buildTree(state)`. Он описывает экраны `main`, `balance` и `transfer`, не выполняя render и не изменяя состояние.

### `src/application.js`

Содержит renderer-independent ядро:

- единый `actionHandlers`;
- `application.dispatch(event)`;
- обработку input через `setByPath`;
- сценарий перевода;
- клиентскую валидацию;
- управление статусом;
- renderer-neutral callback `requestRender()`.

### `src/console-renderer.js`

Рекурсивно отображает общее дерево в консоли и создаёт `actionMap`, связывающий номера пунктов с интерактивными нодами.

### `src/dom-renderer.js`

Рекурсивно преобразует то же дерево в DOM:

- `text` становится `p`;
- `action` становится `button` с `data-intent`;
- `input` становится `input` с `data-bind`;
- `menu` становится `nav`;
- `container` становится `section`.

Текст устанавливается через `textContent`. DOM renderer пока только создаёт элементы и не отправляет события в приложение.

### `src/app.js`

Текущая console entry point. Она создаёт приложение, строит дерево, вызывает console renderer и преобразует ввод пользователя в нормализованные события.

### `src/browser-demo.js`

Текущая незавершённая browser entry point. Она выполняет только одноразовое построение:

```js
const tree = buildTree(state);
renderDOM(tree, root);
```

Она пока не создаёт `application`, не вызывает `application.dispatch(event)` и не выполняет повторный render после изменения состояния.

### `src/server.js`

Это не HTTP-сервер. Файл содержит изолированную имитацию backend API перевода с искусственной задержкой и собственным балансом.

### `src/observer.js` и `src/effects.js`

Observer доставляет события состояния и приложения. Effects подписываются на них и ведут демонстрационный журнал. Эти модули не должны владеть состоянием или renderer.

## Фактическое состояние реализации

Реализовано:

- явный application state;
- пять декларативных типов нод;
- детерминированный `buildTree(state)`;
- renderer-independent application core;
- единый реестр доверенных handlers;
- нормализованные action/input события;
- работающий интерактивный console renderer;
- статический DOM renderer для всех текущих типов нод;
- каналы observer/effects;
- асинхронный демонстрационный сценарий перевода;
- заготовка HTML-страницы и browser entry point.

Не реализовано:

- DOM action/input dispatch;
- повторный DOM render после изменения `state`;
- строгий структурный и семантический валидатор дерева;
- отдельный контракт `InterfaceBuilder`;
- deterministic provider за этим контрактом;
- AI provider;
- allowlist внешних значений `intent` и `bind`;
- безопасный fallback при ошибке builder;
- тесты полного цикла;
- полностью стабильный console render lifecycle.

## Где остановилась работа

Последний зафиксированный этап добавил статический DOM renderer. После него были созданы незакоммиченные:

- `index.html`;
- `styles.css`;
- `src/browser-demo.js`.

Браузер уже показывает начальное дерево, но остаётся статическим. Нажатия кнопок и изменение inputs ничего не передают в приложение.

Текущий разрыв:

```text
state
  → buildTree(state)
  → renderDOM(tree)
  ✕ DOM event
  ✕ application.dispatch(event)
  ✕ new state
  ✕ requestRender()
```

## Ближайшая задача

Нужно завершить один вертикальный DOM-цикл на текущем детерминированном builder:

```text
browser DOM event
  → { type: "action", intent }
    или { type: "input", bind, value }
  → application.dispatch(event)
  → изменение state
  → requestRender()
  → buildTree(state)
  → renderDOM(tree)
```

`renderDOM()` получает не сам `state`, а новое UI-дерево, построенное из его актуального состояния. Сейчас `src/browser-demo.js` выполняет эту последовательность только один раз при загрузке страницы, поэтому статичным является не `state`, а выполненный один раз render.

Требуемая связь:

```js
function render() {
  const tree = buildTree(application.state);
  renderDOM(tree, root);
}

const application = createApplication({
  requestRender: render,
});
```

После значимого изменения состояния `application.js` уже вызывает `requestRender()`. Browser entry point должен связать этот callback с повторным `buildTree(application.state)` и передачей полученного дерева в `renderDOM(tree, root)`.

Минимальный объём:

1. В `src/browser-demo.js` создать приложение через `createApplication({ requestRender })`.
2. Реализовать функцию повторного построения и DOM render.
3. Делегировать `click` от элементов с `data-intent` в action-событие.
4. Делегировать изменение элементов с `data-bind` в input-событие.
5. Все события передавать только в `application.dispatch(event)`.
6. Не переносить handlers или бизнес-логику в browser entry point или DOM renderer.

Согласованный файл ближайшей реализации:

- `src/browser-demo.js`.

На этом шаге не требуется менять:

- `src/dom-renderer.js` — он уже отображает все существующие типы нод;
- `src/application.js` — он уже обновляет state и запрашивает render;
- `src/tree.js` — он уже строит дерево из актуального state;
- `index.html` — он уже подключает browser entry point.

Для этого этапа достаточно Live Server. Отдельный Node HTTP-сервер и синхронизация console/browser не требуются. Console и DOM являются двумя выбираемыми средами исполнения общего архитектурного контракта, а не двумя одновременно синхронизируемыми окнами.

## Порядок дальнейшего развития

После замыкания DOM-цикла:

1. Стабилизировать и протестировать общий render lifecycle.
2. Добавить тесты `application.dispatch(event)`.
3. Формализовать схему UI-дерева.
4. Добавить строгую рекурсивную валидацию типов, обязательных props и дочерних коллекций.
5. Добавить allowlist `intent` и `bind`.
6. Ввести `InterfaceBuilder` и deterministic provider на основе текущего `buildTree`.
7. Добавить безопасный fallback на deterministic provider.
8. Подключить AI provider, возвращающий тот же валидируемый формат.
9. Продемонстрировать полный цикл через console и DOM renderers.

Не следует начинать с генерации HTML, JavaScript, сложного event bus, WebSocket или большого UI-фреймворка. Ценность прототипа заключается в проверке небольшого безопасного цикла с заменяемым builder и renderer.

Console renderer:

```powershell
npm start
```
