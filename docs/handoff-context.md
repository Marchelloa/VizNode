# VizNode — контекст для продолжения разработки

Актуализировано: 13 сентября 2026 года.

## Идея и архитектура

VizNode исследует заменяемый интерфейс, построенный из доверенного состояния и разрешённых действий пользователя. Представление отделено от прикладной логики. Общий замысел описан в README.md и docs/ideas/ai-driven-dom-interface.md.

Node runtime — единственный владелец состояния, application.dispatch(event), доверенных handlers и построения UI-дерева. Console и DOM — представления одного работающего приложения. Браузер не импортирует state, не создаёт application и не строит дерево самостоятельно.

Целевой цикл:

```text
Console event ─┐
               ├→ application.dispatch(event) → state → buildTree(state)
DOM event ─────┘                                         ├→ Console render
                                                        └→ SSE → DOM render
```

Направление DOM event → Node пока не реализовано.

## Контракт представления

state хранит экран, баланс, форму перевода и статус. UI-дерево описывает представление этих данных и не содержит исполняемой бизнес-логики.

Корень дерева — массив нод. Текущие типы: text, action, input, menu (props.items), container (props.children).

Renderer отображает дерево и должен преобразовывать пользовательские действия в нормализованные события:

```js
{ type: "action", intent: "show_balance" }
{ type: "input", bind: "transferForm.amount", value: "500" }
```

Обработчики и изменение состояния остаются в application.dispatch(event). Строгая валидация дерева и allowlist внешних intent/bind пока не реализованы.

## Текущие модули

- src/state.js — общее состояние и setByPath.
- src/nodes.js — фабрики пяти типов нод.
- src/tree.js — детерминированный buildTree(state), экраны main, balance, transfer.
- src/application.js — dispatch, handlers, обработка формы и асинхронный сценарий перевода; вызывает requestRender.
- src/console-renderer.js — вывод дерева и actionMap для Console.
- src/dom-renderer.js — создание DOM из дерева, текст через textContent; действия помечены data-intent, поля — data-bind.
- src/app.js — создание application, Console-ввод, getCurrentTree(), запуск моста; loop() строит дерево один раз, передаёт его в renderConsole и publishTree.
- src/browser-bridge.js — локальный HTTP/SSE-мост на 127.0.0.1:3000, принимает callback getCurrentTree и возвращает server и publishTree.
- src/browser-demo.js — EventSource и renderDOM для входящих деревьев; обработчиков кликов и ввода пока нет.
- src/server.js — имитация backend API перевода с задержкой и собственным балансом; это не HTTP-мост.
- src/observer.js и src/effects.js — уведомления и демонстрационный журнал.
- index.html и styles.css — браузерная страница и оформление.

## Реализованный этап: Node → DOM через SSE

1. Браузер открывает EventSource на http://127.0.0.1:3000/api/events.
2. GET /api/events создаёт SSE-ответ; мост сохраняет response в Set клиентов.
3. Новый клиент сразу получает getCurrentTree(), то есть актуальный экран Console.
4. При очередном loop() одно дерево отображается в Console и отправляется через browserBridge.publishTree(tree).
5. Браузер разбирает event.data как JSON и вызывает renderDOM(tree, root).
6. При закрытии запроса клиент удаляется из Set. EventSource автоматически пытается восстановить потерянное соединение.

GET /api/tree и одноразовый fetch удалены: SSE доставляет и начальное дерево, и обновления. Неизвестные маршруты получают 404. POST-маршрутов пока нет.

Передача getCurrentTree в мост передаёт функцию без вызова. Мост вызывает её при подключении клиента; publishTree получает уже построенное дерево. Замыкания сохраняют доступ к callback и списку клиентов.

## Проверки и ограничения

- В предыдущей сессии отдельно проверена доставка начального дерева и следующего обновления по одному SSE-соединению.
- После подключения EventSource и удаления GET /api/tree проверка синтаксиса browser-bridge.js и browser-demo.js прошла.
- В src больше нет упоминаний /api/tree.
- Сквозная проверка переходов Console → открытый браузер после последних изменений предложена, но её результат пользователем ещё не подтверждён.
- npm test пока является заглушкой; постоянного набора тестов нет.
- Console render lifecycle ещё требует внимания: requestRender вызывает loop(), который также создаёт readline.question. До добавления событий из DOM нужно проверить повторные запросы ввода и устаревшие actionMap.

## Ближайшие шаги

1. Проверить main → transfer → main через Console: DOM должен обновляться без перезагрузки страницы. Проверить подключение новой вкладки на текущем экране.
2. Добавить направление DOM → Node небольшими согласованными шагами:
   - выбрать POST-маршрут (например, /api/dispatch), реализовать чтение JSON, проверку входных событий и CORS/preflight для Live Server;
   - передать в мост callback, вызывающий application.dispatch(event), через src/app.js;
   - добавить делегирование DOM click для data-intent в src/browser-demo.js;
   - подключить data-bind и согласовать фиксацию формы перед action.
3. Проверить единый цикл изменения состояния из обоих renderer, включая перевод и статусы.

Планируемые файлы следующего этапа: src/browser-bridge.js, src/app.js, src/browser-demo.js. Конкретный объём каждой правки согласовывается отдельно; этот список не является разрешением на реализацию.

Незавершённый ввод DOM может оставаться локальным черновиком. Перед действием, зависящим от формы, нужно зафиксировать значения input-событиями и сохранить их порядок относительно action. Повторный DOM render не должен случайно уничтожать незавершённый ввод.

## Дальнейшее развитие

После общего интерактивного цикла: стабилизация render lifecycle, тесты dispatch, строгая схема и рекурсивная валидация дерева, allowlist intent/bind, контракт InterfaceBuilder и deterministic provider, затем необязательный AI provider с безопасным fallback.

AI может выбирать и компоновать разрешённые ноды. Он не должен генерировать исполняемый JavaScript или произвольный HTML, создавать handlers, менять state или обходить dispatch. Его дерево должно проходить валидацию до renderer.

## Запуск

1. npm start — запускает Console и HTTP/SSE-мост.
2. Открыть index.html через Live Server, обычно http://127.0.0.1:5500/index.html.
3. Управлять приложением через Console; браузер пока только отображает входящие деревья.

Закрытие вкладки не останавливает Node. Завершение Console останавливает весь runtime.

Пользователь вводит код самостоятельно, Codex объясняет поток данных и проверяет результат. Изменения файлов Codex выполняет только после явного согласования согласно корневому AGENTS.md. Пользователь отдельно разрешил эту актуализацию документа и коммит текущего SSE-этапа.
