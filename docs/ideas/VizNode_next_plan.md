# VizNode — направление следующего этапа

Актуализировано: 20 октября 2026 года. Последнее обсуждение и точка продолжения — ниже; они уточняют приоритеты общего плана.

## Отправная точка

Основной прототип работает согласно замыслу пользователя: общее состояние и обработчики, декларативное дерево, Console и DOM, HTTP-диспетчеризация и SSE-обновления. DOM-ввод имеет последовательную очередь, сохранение локального текста, фокуса и выделения. Оформление заменяется CSS-пресетами.

Модель использования: одно приложение, Console и одна браузерная вкладка. Поддержка нескольких вкладок и разрешение конфликтов между ними не планируются в текущем объёме. Запрет второго подключения пока не реализован; необходимость такого запрета не решена.

## Цель обсуждения

Понятный API для создания деревьев интерфейса, обработчиков и подключения необходимых механизмов приложения.

Пользователь пока обсуждает направление. Следующие шаги — предложение, а не согласованный объём изменений кода. Конкретные сигнатуры API ещё не выбраны.

## Предлагаемая последовательность

Это общий ориентир сентября. Ближайшее обсуждаемое изменение теперь — вынос обработчиков с сохранением существующего механизма регистрации; см. последнюю секцию.

1. Зафиксировать поведение существующего цикла: быстрый ввод и Submit, повторное нажатие, ошибка input или операции, переход Console → DOM и обратно. Различать принятие события и завершение операции.
2. Описать небольшой второй сценарий, например список задач: состояние, дерево, ввод, обработчик и ошибка. Проверить, что должен знать автор приложения.
3. На этих примерах согласовать минимальный контракт изменения состояния, уведомлений и обновления представления, включая async-обработчики.
4. Отделить универсальные механизмы от банковской логики и проверить второе приложение без изменения ядра. Реализацию согласовывать отдельно.
5. Закрепить выбранные контракты понятными ошибками, документацией, подсказками редактора и целевыми тестами.
6. Развивать валидацию дерева, заменяемый InterfaceBuilder и затем необязательный AI provider. Внешнее дерево должно проверяться до отображения.

Предлагаемый критерий этапа: разработчик создаёт второе небольшое приложение через состояние, дерево и обработчики, использует готовые Console/DOM-механизмы и не правит ядро VizNode.

## Ограничения, влияющие на API

- createApplication импортирует конкретный state и создаёт банковский demo-сервер.
- Изменение состояния, уведомление и render вызываются отдельно.
- submit_transfer запускает flow через void; dispatch не ждёт окончания перевода.
- В ядре нет защиты от повторного Submit во время отправки.
- После ошибки input очередь может выполнить action со старым значением; pending-ввод требует правил восстановления.
- Валидация внешних событий и дерева пока неполная.
- npm test — заглушка; проверки под задержками не зафиксированы как завершённые.

## Что не является ближайшей задачей

Поддержка нескольких вкладок, расширение набора тем и превращение прототипа в большой UI-фреймворк. База данных, новый транспорт или AI не нужны для проверки удобства базового API.

Текущее устройство описано в [карте проекта](../project-map.md), подробные ограничения — в [контексте продолжения](../handoff-context.md).

## Обсуждение 18–20 октября: API дерева и обработчиков

### Цель и принципы

VizNode — прототип идеи заменяемого интерфейса, а не учебный проект. Пользователь самостоятельно разбирает поток и контролирует архитектуру. После перерыва нужно восстанавливать актуальный контекст по документации и коду, а не предлагать повторно реализовать уже работающий DOM-ввод.

Основной акцент обсуждения: чёткие границы ответственности и контракты позволяют работать с отдельной частью растущего проекта, не удерживая всю реализацию в голове. Контракт включает не только аргументы и результат, но и изменение состояния, уведомления, перерисовку, ошибки и смысл завершения async-действия.

Сейчас автор приложения вручную согласует дерево, строковые intent, реестр обработчиков, bind и запросы render. Цель будущего API — сделать создание приложения понятнее и уменьшить вероятность рассогласования этих частей.

### Как устроено сейчас

- src/tree.js описывает структуру экранов main, balance и transfer через buildTree(currentState); экран выбирается по currentState.screen.
- src/nodes.js предоставляет фабрики отдельных нод.
- actionNode(id, label, intent) сохраняет intent в декларативной ноде; если третий аргумент не задан, intent берётся из id.
- Адаптер отправляет `{ type: "action", intent }`, а application.dispatch находит функцию в actionHandlers по этому ключу и вызывает её.
- В дереве хранится идентификатор действия, а не исполняемая функция. Для input связь задаётся путём bind в состоянии.
- createApplication({ requestRender }) возвращает объект с state, actionHandlers и dispatch.
- Возвращённый actionHandlers и реестр внутри dispatch — один объект, поэтому добавление свойства с функцией после создания приложения доступно диспетчеру.
- Текущий dispatch вызывает handler() без аргументов. Контекст `{ state, update }` пока не реализован.

Допустимый в текущем механизме пример:

```js
const app = createApplication({ requestRender });

app.actionHandlers["my_action"] = () => {
  console.log("Действие выполнено");
};

// Соответствующая нода:
actionNode("my_action", "Моё действие");
```

Прямое присваивание пока не проверяет тип значения и не предотвращает случайную перезапись обработчика. Не следует путать добавление свойства в общий объект с заменой всего app.actionHandlers новым объектом: замкнутый внутри dispatch реестр при такой замене автоматически не изменится.

### Обсуждённый, но не выбранный API

Рассматривался класс Application с initialState, регистрацией экранов через app.screen(), обработчиков через app.actions() и запуском через app.start(). Фабрики ui.action/ui.input могли бы принимать объект параметров; значения input можно было бы получать по bind автоматически.

```js
// Только эскиз будущего API — сейчас таких методов нет.
const app = new Application({ initialState });
app.screen("main", ({ state }) => [
  ui.action({ label: "Перевести", intent: "open_transfer" }),
]);
app.actions({
  open_transfer({ update }) {
    update({ screen: "transfer" });
  },
});
app.start({ console: true, browser: { port: 3000 } });
```

В этом эскизе update объединял бы изменение состояния, уведомление и обновление представлений. Также обсуждался вариант регистрации одного действия с возвратом ссылки, которую можно передавать фабрике ноды вместо повторения строки intent. Ни класс, ни методы, ни способ связи действий окончательно не выбраны.

Предложено сначала выразить существующий банковский сценарий через предполагаемый API без переделки ядра, затем проверить удобство на втором небольшом приложении. Класс сам по себе не обеспечивает стабильность; важны контракты.

### Отсутствующие обработчики

Пользователь хочет понятную подсказку, если action-нода подразумевает действие, а функция не подключена.

Предложенный текст:

```text
[VizNode] Экран "transfer": действие "Отправить"
с intent "submit_transfer" не имеет обработчика.
Привяжите функцию к этому действию.
```

Обсуждались два уровня: предупреждение при проверке построенного дерева и отказ при dispatch отсутствующего действия. Одинаковые предупреждения не должны засорять консоль при каждом render. Слово «заглушка» предложено использовать только для намеренно заданной заглушки; отсутствие функции не считать успешным выполнением. Это предложения, реализация и точный момент проверки не согласованы.

Чтобы подключить поведение уже существующей action-ноды, достаточно добавить соответствующий обработчик в реестр. Но сама диагностика требует отдельной реализации в dispatch и/или проверке дерева.

## Последняя точка остановки: вынести обработчики без нового API

Пользователь предложил пока оставить createApplication и существующий actionHandlers, а текущие встроенные обработчики вынести в отдельный файл, добавляя их в реестр после создания приложения.

Предпочитаемое направление обсуждения:

```text
создать application
  → подключить функции из отдельного модуля к app.actionHandlers
  → использовать прежние intent и dispatch
```

Отдельный файл может экспортировать объект именованных функций или функцию подключения. Способ экспорта и передачи зависимостей ещё предстоит выбрать. В будущем обработчики можно разделять по нескольким модулям.

Codex предложил иной вариант: registerActionHandlers(...) вызывать внутри application.js, передавая actionHandlers, state, requestRender, notifyStateChanged, notifyAppEvent и submitTransferFlow. При этом четыре обработчика show_balance, open_transfer, submit_transfer и back переехали бы в src/action-handlers.js, а submitTransferFlow остался бы в application.js.

Этот вариант НЕ согласован. Пользователь остановил переход к реализации словами: «подожди не торопись. пока обсуждаем и прорабатываем». Codex признал отличие своего варианта от предложенной пользователем внешней регистрации после createApplication.

### С чего продолжить на другом компьютере

1. Прочитать актуальные application.js и app.js: проверить возвращаемый реестр и зависимости текущих обработчиков.
2. Обсудить именно внешнее наполнение app.actionHandlers после createApplication, не начинать автоматически с класса или внутренней registerActionHandlers.
3. Разобрать, как внешние функции получат state, requestRender, уведомления и доступ к submitTransferFlow: сейчас они используют окружение application.js. Простого перемещения текста функций недостаточно.
4. Определить границу переноса: только четыре обработчика или также банковский flow; пока граница не выбрана.
5. Показать небольшой пример регистрации и вызова, объяснить зависимости и компромиссы.
6. Только после отдельного согласования менять исходники.

На момент этой записи изменения исходников в рамках последнего обсуждения не выполнялись. Пользователь разрешил только сохранить контекст в этом документе. Коммит и реализация нового API этим разрешением не предусмотрены.
