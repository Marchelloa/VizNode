# VizNode — AI-driven DOM-интерфейс

## Статус документа

Этот документ описывает текущую задачу прототипа. Общая база событий и обработчиков уже реализована, а DOM renderer, валидатор дерева и AI provider пока остаются следующими этапами.

## Цель

Проверить главный архитектурный цикл VizNode:

```text
state → AI-интерфейс → DOM → intent → handler → новый state
```

ИИ строит представление текущего состояния приложения, пользователь выбирает действие в DOM, а приложение выполняет заранее определённый обработчик этого действия.

## Почему это подходит для текущего этапа

Задача проверяет основную идею прототипа целиком, но не требует заранее создавать полноценный UI-фреймворк.

Она позволяет проверить:

- можно ли строить интерфейс на основе текущего `state`;
- может ли ИИ выбирать подходящую композицию разрешённых UI-нод;
- сохраняется ли контролируемая связь между DOM-действием и прикладной логикой;
- может ли интерфейс перестраиваться после изменения состояния.

## Текущее состояние прототипа

Сейчас консольный интерфейс строится по цепочке:

```text
state
  ↓
buildTree(state)
  ↓
дерево интерфейса
  ↓
renderConsole(tree)
  ↓
консольное представление и выбор пользователя
  ↓
унифицированное action/input-событие
  ↓
application.dispatch(event)
```

Выбранная пользователем action-нода обрабатывается так:

```text
{ type: "action", intent }
  ↓
application.dispatch(event)
  ↓
actionHandlers[intent]
  ↓
вызов доверенного обработчика
  ↓
изменение state
```

Центральная точка диспетчеризации находится в `src/application.js`:

```js
const handled = await application.dispatch({
  type: "action",
  intent,
});
```

Внутри приложения используется единственный доверенный реестр:

```js
const handler = actionHandlers[event.intent];

if (handler) {
  await handler();
}
```

## Предлагаемая концепция

В прототип добавляется объект, отвечающий за построение визуального интерфейса на основе текущего `state`.

Его условный публичный API:

```js
const tree = await interfaceBuilder.buildTree(state);
```

Конкретное имя класса на этом этапе не принципиально:

```js
const interfaceBuilder = new AI(...);
```

или:

```js
const interfaceBuilder = new AIInterfaceBuilder(...);
```

Важны ответственность объекта и контракт метода `buildTree(state)`.

## Полный цикл работы

```text
текущий state
  ↓
buildTree(state)
  ↓
ИИ создаёт декларативное описание интерфейса
  ↓
приложение проверяет результат
  ↓
проверенное описание преобразуется в DOM
  ↓
пользователь выбирает действие
  ↓
из DOM извлекается intent
  ↓
actionHandlers[intent]
  ↓
обработчик изменяет state
  ↓
интерфейс строится повторно
```

## Входные данные для ИИ

Объект построения интерфейса передаёт модели:

- текущее состояние приложения;
- описание доступных типов UI-нод;
- список разрешённых `intent`;
- правила построения интерфейса;
- схему ожидаемого результата.

Условный пример:

```js
const tree = await model.generateInterface({
  state,
  allowedIntents: Object.keys(application.actionHandlers),
  allowedBindings: [
    "transferForm.recipient",
    "transferForm.amount",
  ],
  allowedNodeTypes: [
    "text",
    "input",
    "action",
    "menu",
    "container",
  ],
});
```

ИИ не получает возможность создавать новые обработчики. Он может только выбрать один из известных приложению `intent`.

## Результат работы ИИ

ИИ возвращает не исполняемый JavaScript и не произвольный HTML, а декларативное описание интерфейса в существующем формате. Корнем остаётся массив нод:

```js
[
  {
    type: "text",
    props: {
      text: "Подтверждение перевода",
    },
  },

  {
    type: "menu",
    props: {
      title: "Действия",
      items: [
        {
          type: "action",
          props: {
            id: "submit_transfer",
            label: "Подтвердить",
            intent: "submit_transfer",
          },
        },
        {
          type: "action",
          props: {
            id: "back",
            label: "Назад",
            intent: "back",
          },
        },
      ],
    },
  },
]
```

Это описание является промежуточным представлением между моделью и DOM.

## Построение DOM

DOM создаётся обычным контролируемым кодом приложения:

```js
function renderAction(node) {
  const button = document.createElement("button");

  button.textContent = node.props.label;
  button.dataset.intent = node.props.intent;

  return button;
}
```

Результат:

```html
<button data-intent="submit_transfer">
  Подтвердить
</button>
```

ИИ не создаёт исполняемый JavaScript и не регистрирует произвольные обработчики событий.

## Обработка действий пользователя

При выборе DOM-элемента renderer должен сформировать такое же событие, какое уже создаёт console adapter:

```js
await application.dispatch({
  type: "action",
  intent: element.dataset.intent,
});
```

`actionHandlers` уже вынесен из console entry point в общее прикладное ядро `application.js`:

```js
const actionHandlers = {
  show_balance() {
    // Существующая логика.
  },

  open_transfer() {
    // Существующая логика.
  },

  submit_transfer() {
    void submitTransferFlow();
  },

  back() {
    // Существующая логика.
  },
};
```

Console и будущий DOM не должны создавать собственные копии этого реестра. Разрешённые AI-намерения можно получать из общей базы:

```js
Object.keys(application.actionHandlers);
```

## Граница ответственности

### ИИ отвечает за

- выбор представления текущего состояния;
- композицию доступных UI-нод;
- подписи и организацию элементов;
- выбор подходящего `intent` из разрешённого списка.

### Приложение отвечает за

- хранение настоящего `state`;
- описание разрешённых UI-нод и `intent`;
- проверку результата ИИ;
- создание настоящего DOM;
- обработку пользовательских событий;
- выполнение `actionHandlers[intent]`;
- изменение состояния;
- повторное построение интерфейса.

## Проверка результата

Результат ИИ необходимо проверить до построения DOM.

Например, action-нода не может содержать неизвестный `intent`:

```js
function validateActionNode(node) {
  const intent = node.props?.intent;

  if (!Object.hasOwn(application.actionHandlers, intent)) {
    throw new Error(`Unknown action intent: ${intent}`);
  }
}
```

Также должны проверяться:

- структура дерева;
- тип каждой ноды;
- обязательные свойства нод;
- типы значений;
- допустимость связей и путей для input-нод.

## Ограничения безопасности

- ИИ использует только разрешённые типы нод.
- ИИ использует только известные `intent`.
- Неизвестный `intent` не выполняется.
- Сгенерированный JavaScript не исполняется.
- Текстовые значения устанавливаются через `textContent`.
- Бизнес-логика остаётся в доверенном коде приложения.
- Результат модели не используется до прохождения проверки.

## Объём первой реализации

Уже выполнено:

1. Сохранить существующий `state`.
2. Создать единый `actionHandlers` в renderer-independent ядре.
3. Ввести `application.dispatch(event)`.
4. Нормализовать console action/input в общие события.
5. Отделить console entry point от прикладной логики.
6. Ввести renderer-neutral callback `requestRender()`.

Следующая часть первой версии:

1. Добавить объект с методом `buildTree(state)`.
2. Сначала подключить статический provider на основе текущего `buildTree`.
3. Проверять типы нод, значения `intent` и пути `bind`.
4. Преобразовывать проверенное дерево в DOM.
5. Передавать DOM action/input в существующий `application.dispatch(event)`.
6. После изменения `state` повторно строить активное представление.
7. Добавить AI provider, возвращающий тот же формат дерева.

## Что пока не входит в задачу

На текущем этапе не требуется:

- менять существующую прикладную логику;
- переписывать `submitTransferFlow()`;
- делать обработчики универсальными;
- создавать отдельный файл для каждой функции;
- разрешать ИИ генерировать JavaScript;
- строить полноценный UI-фреймворк;
- реализовывать оптимальное частичное обновление DOM.

## Критерии готовности

Задачу можно считать выполненной, если:

- текущий `state` может быть представлен в DOM;
- смена `state.screen` приводит к изменению экрана;
- action-ноды становятся интерактивными DOM-элементами;
- выбор действия извлекает правильный `intent`;
- вызывается соответствующий `actionHandlers[intent]`;
- неизвестные `intent` отклоняются;
- обработчик изменяет `state`;
- DOM перестраивается по обновлённому состоянию;
- существующая логика обработчиков не изменена.

## Итог

Эта задача подходит для следующего этапа прототипа, потому что проверяет полный замкнутый цикл:

```text
state → AI-интерфейс → DOM → intent → handler → новый state
```

Основная ценность прототипа заключается именно в проверке этого цикла. Детали организации файлов, окончательные названия классов и дальнейшее разделение функций можно определить после подтверждения работоспособности подхода.
